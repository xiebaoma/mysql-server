# BRR优化方案一期 任务排期

## 1. 一期目标

一期目标是交付一个可被用户正常开启和关闭的 Binlog Realtime Replication（BRR）能力，优先适配部分长耗时 InnoDB DDL，使备库可以在原始 binlog DDL 到达前提前执行主要耗时阶段，从而降低 DDL 复制延迟。

一期不追求覆盖所有 DDL，核心要求是：

- 支持的 DDL 能走 BRR 路径并降低延迟。
- 不支持或异常场景自动回退到原有复制链路。
- 持久 binlog 和 relay log 格式不变，不影响 CDC、mysqlbinlog、级联复制的基础兼容性。
- 用户可以通过开关、状态、日志判断 BRR 是否生效以及为什么 fallback。

## 2. 排期假设

- 总周期：14 周。
- 研发模式：单主线开发，按阶段合入，持续补充 MTR/单测/故障注入测试。
- 一期范围：GTID_MODE=ON、InnoDB 普通表、单 channel、单个 in-flight BRR DDL。
- 一期优先支持：`ALTER TABLE ... ADD INDEX`，以及少量可明确识别的 rebuild/copy 类 `ALTER TABLE`。
- 一期默认 fallback：任何判断不确定、运行失败、断连、版本不兼容场景，均回退到原始 relay log DDL 执行。

## 4. 详细任务拆解

### 第 1 周：需求冻结与详细设计

目标：把一期“做什么、不做什么、失败怎么退”彻底冻结，避免研发过程中范围膨胀。

具体任务：

- 梳理一期用户场景：
  - 长耗时 `ALTER TABLE ... ADD INDEX`。
  - 长耗时 copy/rebuild 类 `ALTER TABLE`。
  - 主备规格接近、DDL 是主要复制延迟来源的场景。
- 明确一期不支持场景：
  - 非 InnoDB。
  - 临时表、系统表、mysql schema 表。
  - 多个 BRR DDL 并发。
  - 跨版本 BRR 协议兼容。
  - failover 后继续接管 in-flight BRR DDL。
  - DML 实时复制。
- 定义 DDL 白名单规则：
  - SQL command 类型。
  - 表类型。
  - storage engine。
  - DDL algorithm。
  - 是否涉及 FK、partition、rename、generated column、fulltext/spatial index 等复杂能力。
- 设计 BRR 状态机：
  - `INIT`
  - `PREPARE_SENT`
  - `PREPARE_RECEIVED`
  - `EXECUTING`
  - `WAIT_SOURCE_RESULT`
  - `COMMIT_RECEIVED`
  - `COMMITTING`
  - `COMMITTED`
  - `ROLLBACK_RECEIVED`
  - `ROLLING_BACK`
  - `FALLBACK`
  - `ABORTED`
- 设计源端状态转换：
  - 进入 BRR。
  - 发送 prepare。
  - DDL 主体执行成功。
  - 发送 commit。
  - DDL 执行失败。
  - 发送 rollback。
  - 发送失败后如何继续原始链路。
- 设计备端状态转换：
  - 接收 prepare。
  - 等待依赖。
  - 执行 DDL。
  - 等待 commit/rollback。
  - 提交并写入 gtid_executed。
  - 失败释放 GTID 并 fallback。
- 定义 BRR event 字段：
  - event version。
  - channel id。
  - DDL id。
  - GTID。
  - query。
  - schema/table。
  - DDL type。
  - DDL algorithm。
  - prepare dependency GTID set。
  - commit dependency GTID set。
  - session variables。
  - source result/error。
- 明确验收指标：
  - 正确性：不丢、不重、不乱序。
  - fallback：失败后原始 SQL worker 可继续执行。
  - 性能：支持 DDL 的复制延迟显著下降。
  - 兼容：binlog/relay log 持久格式不变。

阶段产出：

- `BRR一期详细设计.md`
- `BRR一期DDL白名单.md`
- `BRR状态机.md`
- `BRR异常处理矩阵.md`

### 第 2 周：PoC 验证

目标：验证最大风险点，避免直接进入大规模实现后发现协议不可行。

具体任务：

- PoC 1：验证源端提前 GTID。
  - 在 DDL 执行前生成或确认最终 GTID。
  - 验证原始 binlog 仍写入同一个 GTID。
  - 验证失败回滚时 GTID ownership 可正确释放。
- PoC 2：验证 BRR event 非持久传输。
  - 从 source dump thread 向 replica IO thread 发送一类临时 event。
  - replica 不写入 relay log，仅放入内存 queue。
  - 普通复制事件仍按原逻辑处理。
- PoC 3：验证备库独立 worker 执行 DDL。
  - 创建 BRR worker THD。
  - 设置 slave thread 上下文。
  - 设置 `gtid_next`。
  - 执行一条 `ALTER TABLE ... ADD INDEX`。
- PoC 4：验证 SQL worker GTID auto-skip。
  - BRR worker 提前把 GTID 加入 `gtid_executed`。
  - SQL worker 后续读到原始 GTID_EVENT/QUERY_EVENT。
  - 原 DDL 被跳过，relay log 坐标正常推进。
- PoC 5：验证 fallback。
  - BRR worker 人工失败。
  - 释放 GTID。
  - SQL worker 正常执行原始 DDL。

阶段产出：

- PoC 代码分支。
- PoC 结论文档。
- `BRR第二周PoC验证结论.md`。
- 必须在第 2 周结束前确认：
  - 提前 GTID 是否可控。
  - BRR worker 是否可复用现有 SQL 执行路径。
  - SQL worker skip 是否无需大改。
  - fallback 是否可证明正确。

### 第 3-4 周：BRR event 与实时传输通道

目标：完成 BRR event 的协议、编解码、能力协商和传输路径。

具体任务：

- 新增 BRR event 类型：
  - `BRR_DDL_PREPARE_EVENT`
  - `BRR_DDL_COMMIT_EVENT`
  - `BRR_DDL_ROLLBACK_EVENT`
- 实现 event 编码：
  - 固定 header。
  - version。
  - payload length。
  - DDL id。
  - GTID。
  - dependency GTID set。
  - query length/query。
  - session variables。
  - error code/error message。
- 实现 event 解码：
  - version 检查。
  - length 检查。
  - checksum 或基础完整性检查。
  - 不兼容 version 直接忽略并 fallback。
- 增加 source/replica 能力协商：
  - replica 请求 dump 时携带 BRR capability。
  - source 根据 capability 和本地开关决定是否启用。
  - 未协商成功时不发送 BRR event。
- 修改 source dump thread：
  - 支持从 BRR buffer 中取 event。
  - 保证 BRR event 可以在原始 binlog event 前发送。
  - 保证普通 binlog 读取和发送逻辑不受影响。
- 修改 replica IO thread：
  - 识别 BRR event。
  - 不写 relay log。
  - 写入 BRR queue/cache。
  - 唤醒 BRR worker。
- 处理断连：
  - IO thread 断开时清理未完成的 BRR event。
  - 重连后不依赖旧 BRR event，继续从原始 relay log 恢复。
- 增加基础测试：
  - capability on/off。
  - source on/replica off。
  - source off/replica on。
  - BRR event decode 失败。
  - BRR event 不进入 relay log。

阶段产出：

- BRR event 编解码实现。
- dump/io 通道支持。
- MTR：能力协商与 event 传输测试。

### 第 5-6 周：源端 DDL hook 与白名单

目标：源端能够识别支持的 DDL，在正确生命周期发送 BRR prepare/commit/rollback。

具体任务：

- 增加 BRR DDL eligibility 判断：
  - 是否开启 BRR。
  - 是否 GTID_MODE=ON。
  - 是否 binlog enabled。
  - 是否 statement DDL。
  - 是否 InnoDB 普通表。
  - 是否在白名单中。
  - 是否单表。
  - 是否非临时表。
  - 是否非系统表。
  - 是否当前没有其他 in-flight BRR DDL。
- 在 DDL 执行路径中加入 BRR context：
  - DDL id。
  - GTID。
  - query。
  - table metadata。
  - start timestamp。
  - dependency GTID set。
  - fallback reason。
- 实现提前 GTID：
  - 在进入 BRR 前确定该 DDL 的最终 GTID。
  - 确保后续原始 binlog 写入使用同一 GTID。
  - DDL 失败时释放或按现有 GTID rollback 逻辑处理。
- 实现 prepare 发送时机：
  - 完成解析、权限、基础语义检查后。
  - 完成白名单判断后。
  - 在长耗时 copy/rebuild/inplace 阶段前。
  - 如果不能确定安全时机，直接 fallback。
- 实现 commit 发送时机：
  - 源端 DDL 主体成功。
  - 即将进入最终提交/rename/DD commit 阶段。
  - 采集 commit dependency GTID set。
- 实现 rollback 发送时机：
  - 源端 DDL 执行失败。
  - 源端 DDL 被 kill。
  - 源端中途发现无法继续 BRR。
- 保证原始 binlog 写入不变：
  - 原始 `GTID_EVENT + QUERY_EVENT` 正常写入。
  - BRR event 不落盘。
- 增加源端 fallback reason：
  - unsupported DDL。
  - unsupported engine。
  - no GTID。
  - BRR capability off。
  - another BRR DDL running。
  - prepare send failed。
  - unsafe DDL phase。
- 增加测试：
  - 支持 DDL 进入 BRR。
  - 不支持 DDL fallback。
  - prepare 发送失败 fallback。
  - 源端 DDL 失败发送 rollback。
  - 原始 binlog 不变化。

阶段产出：

- 源端 DDL hook 实现。
- DDL 白名单实现。
- 提前 GTID 初版。
- MTR：源端 DDL 生命周期测试。

### 第 7-8 周：备端 BRR worker 与 DDL 预执行

目标：备端能够消费 BRR event，提前执行 DDL 主体，并根据源端结果提交或清理。

具体任务：

- 新增 BRR worker 生命周期：
  - channel start 时启动。
  - channel stop 时停止。
  - IO thread 断连时进入 fallback/清理。
  - server shutdown 时安全退出。
- 新增 BRR queue/cache：
  - 按 DDL id 组织。
  - 记录 prepare/commit/rollback。
  - 记录状态。
  - 记录错误。
  - 一期只允许一个 active DDL。
- 实现 prepare 处理：
  - 校验 event version。
  - 校验 DDL id。
  - 校验 GTID。
  - 校验本地 capability。
  - 校验 DDL 是否仍在本地白名单。
  - 占有 GTID。
  - 等待 prepare dependency。
  - 构造执行 THD。
  - 设置 session variables。
  - 执行 DDL 主体。
- 实现 commit 处理：
  - 校验 DDL id 和 GTID。
  - 等待 commit dependency。
  - 完成 DDL 提交。
  - 将 GTID 加入 `gtid_executed`。
  - 释放 GTID ownership。
  - 清理 BRR queue。
- 实现 rollback 处理：
  - 校验 DDL id 和 GTID。
  - 回滚 DDL 或清理中间对象。
  - 释放 GTID ownership。
  - 标记 fallback 或 aborted。
- 实现 BRR worker 执行上下文：
  - `system_thread` 标识。
  - `slave_thread` 标识。
  - `rli_slave`。
  - `server_id`。
  - `gtid_next`。
  - 当前 db。
  - sql mode。
  - charset/collation。
  - time zone。
  - foreign_key_checks。
  - unique_checks。
- 支持执行失败 fallback：
  - 不把 GTID 加入 executed。
  - 释放 ownership。
  - 等待 SQL worker 执行原始 DDL。
- 增加测试：
  - BRR worker 成功执行 `ALTER TABLE ADD INDEX`。
  - BRR worker 执行失败后 SQL worker 兜底。
  - BRR worker 等待源端 commit。
  - BRR worker 收到 rollback。
  - BRR worker stop/start。

阶段产出：

- BRR worker 初版。
- BRR queue/cache。
- MTR：备库预执行与 commit/rollback 测试。

### 第 9 周：GTID 协调与 SQL worker 跳过

目标：BRR worker 与现有 SQL worker 在 GTID ownership、gtid_executed、auto-skip 上正确协作。

具体任务：

- 梳理现有 GTID ownership 生命周期：
  - `set_gtid_next`
  - `acquire_ownership`
  - `gtid_pre_statement_checks`
  - `gtid_end_transaction`
  - `gtid_executed` 更新。
- BRR worker 获取 GTID ownership：
  - prepare 阶段占有 GTID。
  - 如果 GTID 已 executed，直接跳过 BRR。
  - 如果 GTID 被其他线程占有，等待或 fallback。
- BRR worker 释放 GTID ownership：
  - commit 成功后加入 executed。
  - rollback/fallback 时不加入 executed。
  - 异常退出必须释放 ownership。
- SQL worker 行为：
  - 读到原始 GTID 时，如果 GTID 被 BRR worker 占有，等待。
  - BRR commit 后，SQL worker 进入 auto-skip。
  - BRR fallback 后，SQL worker 正常执行原始 DDL。
- 并行复制约束：
  - 一期不支持多个 BRR DDL 并发。
  - BRR DDL 与普通 worker 的依赖等待必须基于 GTID set。
  - 必要时让 DDL group 进入 isolated 模式，降低并行复制复杂度。
- 增加测试：
  - SQL worker 等待 BRR worker 释放 GTID。
  - BRR commit 后 SQL worker skip。
  - BRR fallback 后 SQL worker execute。
  - `gtid_executed` 正确推进。
  - stop replica 时等待线程可退出。

阶段产出：

- GTID ownership 集成。
- SQL worker skip 链路闭环。
- MTR：GTID 协调测试。

### 第 10 周：异常恢复与 fallback

目标：确保 BRR 失败不会破坏复制正确性。

具体任务：

- prepare 发送失败：
  - 源端记录 fallback。
  - 不创建 in-flight BRR 状态。
  - 备端不感知，走原始复制。
- prepare 已收到但 commit/rollback 未收到：
  - IO 断连后 BRR worker 停止等待。
  - 清理本地未提交状态。
  - 释放 GTID。
  - 等待原始 relay log DDL。
- BRR worker 执行失败：
  - 记录失败原因。
  - 清理中间对象。
  - 释放 GTID。
  - 标记该 DDL fallback。
- 源端 DDL 失败：
  - 源端发送 rollback。
  - 备端 rollback 或清理。
  - 原始 binlog 不写成功 DDL。
- replica crash：
  - 启动时扫描/清理 BRR 临时对象。
  - 清空内存 BRR queue。
  - 依赖 relay log 继续恢复。
- source crash：
  - 备端连接断开。
  - BRR worker 不永久等待。
  - 清理后 fallback。
- SQL thread stop：
  - BRR worker 跟随 channel 停止。
  - 不能留下 GTID ownership。
- SQL thread start：
  - 不恢复旧 BRR in-flight。
  - 从 relay log 原始 DDL 继续。
- timeout 策略：
  - prepare 后等待 commit/rollback 超时。
  - 等待 dependency 超时。
  - 等待 GTID ownership 超时。
  - 超时均进入 fallback 或停止复制并报错，具体按安全性选择。
- 增加故障注入点：
  - source prepare 后 crash。
  - source commit 前 crash。
  - replica prepare 后 crash。
  - replica DDL 执行中 crash。
  - BRR worker commit 前 crash。
  - SQL worker 等待 GTID 时 stop replica。

阶段产出：

- fallback 实现。
- crash recovery 清理逻辑。
- 故障注入测试。
- 异常处理矩阵更新。

### 第 11 周：开关、状态与可观测性

  - `binlog_realtime_replication`
  - `binlog_realtime_replication_ddl`
  - `binlog_realtime_replication_ddl_timeout`
  - `binlog_realtime_replication_fallback_on_error`
- 新增状态变量：
  - `Brr_ddl_attempts`
  - `Brr_ddl_success`
  - `Brr_ddl_fallback`
  - `Brr_ddl_rollback`
  - `Brr_ddl_errors`
- 新增状态展示：
  - 当前是否启用 BRR。
  - 当前 channel 是否协商 BRR。
  - 当前 in-flight DDL id。
  - 当前 BRR 状态。
  - 当前 BRR DDL query 摘要。
  - 最近一次 fallback reason。
  - 最近一次 error code。
- 可选新增 performance schema 表：
  - `replication_brr_status`
  - `replication_brr_history`
- 错误日志：
  - BRR enabled/disabled。
  - capability negotiation result。
  - DDL enters BRR。
  - DDL fallback reason。
  - BRR worker failure。
  - BRR cleanup result。
- 管理命令：
  - 一期可以不新增 SQL 命令。
  - 如需要，可通过变量关闭 BRR 并等待当前 DDL 结束。
- 增加测试：
  - 开关动态关闭。
  - BRR 状态变量增长。
  - fallback reason 可见。
  - 日志包含必要信息。

阶段产出：

- 用户开关。
- 状态变量/P_S 或 SHOW 扩展。
- 运维可观测性测试。

### 第 12 周：集成测试与故障注入

目标：把前面各模块串起来做系统验证。

具体任务：

- 正常链路测试：
  - source 开启、replica 开启。
  - 支持 DDL 走 BRR。
  - 不支持 DDL fallback。
  - 多次连续 DDL。
  - DDL 前后 DML 正确复制。
- 延迟收益测试：
  - 大表 `ADD INDEX`。
  - 大表 rebuild。
  - 备库执行比主库快。
  - 备库执行比主库慢。
  - 主备负载不同。
- 顺序正确性测试：
  - DDL 前 DML。
  - DDL 后 DML。
  - Online DDL 并发 DML。
  - Copy DDL 阻塞 DML。
- GTID 测试：
  - GTID ownership 等待。
  - GTID executed skip。
  - GTID already executed。
  - restart 后 GTID set 正确。
- 复制生命周期测试：
  - stop replica。
  - start replica。

## 6. 风险与预案

### 风险 1：提前 GTID 改造影响过大

影响：源端无法在 prepare 阶段告诉备库最终 GTID，BRR worker 无法提前占有 GTID。

预案：

- 一期只对 BRR DDL 提前分配 GTID，避免影响普通事务。
- 如果提前 GTID 风险不可接受，改为 BRR 内部 pending id + 原始 GTID 到达后再绑定，但一期收益会下降。
- 第 2 周 PoC 必须给出结论，不能拖到主实现阶段。

### 风险 2：DDL 无法安全暂停在提交前

影响：备库无法做到“主体先执行、提交等源端结果”。

预案：

- 一期先支持能够明确拆分主体和提交阶段的 DDL。
- 对无法拆分的 DDL 直接 fallback。
- 优先支持 `ADD INDEX` 这类收益明确且路径相对可控的操作。

### 风险 3：异常恢复复杂度超出预期

影响：BRR crash 后可能留下中间对象或 GTID ownership。

预案：

- 一期不持久化 BRR in-flight 状态。
- crash/reconnect 后统一清理并走原始 relay log。
- BRR 中间对象命名必须可识别、可清理。

### 风险 4：并行复制顺序冲突

影响：BRR worker 与普通 SQL worker 之间可能出现 DDL/DML 顺序错误。

预案：

- 一期只允许一个 BRR DDL。
- 对 DDL dependency GTID set 做严格等待。
- 必要时让 DDL 所在 group isolated，牺牲部分并行度换正确性。

### 风险 5：白名单过宽导致正确性风险

影响：某些 DDL 在主备执行路径不一致，产生数据或元数据差异。

预案：

- 白名单宁窄勿宽。
- 所有未明确验证的 DDL fallback。
- 每扩展一个 DDL 子类必须补充 MTR 和故障注入测试。

## 8. 一期完成定义

一期完成需要同时满足：

- 用户可以通过参数开启/关闭 BRR。
- 支持的 DDL 可以在备库提前执行并降低复制延迟。
- 不支持 DDL、异常 DDL、断连、crash 场景不会破坏原始复制。
- 原始 binlog/relay log 持久格式不变。
- SQL worker 能正确跳过 BRR 已提交的 DDL。
- BRR fallback 后 SQL worker 能正常执行原始 DDL。
- 有完整状态、日志、统计和排查文档。
- 有覆盖正常链路、fallback、GTID、crash、stop/start 的测试。
