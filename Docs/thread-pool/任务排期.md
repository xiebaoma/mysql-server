# MySQL Thread Pool 任务排期

## 1. 排期假设

本排期从 2026-05-21 开始，按 10 周推进，目标是在第 10 周结束时形成可进入大规模回归和压测的 thread pool 分支。

默认投入：

- 开发 A：连接处理器、THD 生命周期、shutdown/KILL。
- 开发 B：thread group、listener、epoll/poll、队列。
- 开发 C：stall、oversubscribe、优先级、系统变量和观测。
- 测试/性能：MTR、单元测试、sysbench、慢客户端和锁等待场景。

每个工作日按两个时间段安排：

- 上午：设计确认、核心编码、接口联调。
- 下午：补测试、修边界、代码审查和当日验收。

## 4. 风险缓冲

| 风险 | 预留处理时间 | 处理策略 |
|------|--------------|----------|
| `do_command()` 阻塞网络读/写语义复杂 | 第 5 周 2 天 | 先保证 idle read 由 listener 接管，写阻塞作为已知风险进入 stall/后续非阻塞写 |
| KILL/shutdown 与 fd rearm 竞态 | 第 5 周 1 天，第 10 周 1 天 | 引入明确状态机和 fd owner，所有关闭路径统一摘除 fd |
| oversubscribe 导致线程数失控 | 第 6 周 2 天 | per-group 阈值、全局上限、创建节流同时生效 |
| 优先级导致 Low Queue 饥饿 | 第 7 周 1 天 | tickets + aging 双保险 |
| 性能不达预期 | 第 9 周 3 天 | 先确认线程数、上下文切换、队列延迟，再调参数，不急于改执行层 |

## 5. 阶段验收标准

### Phase 1 验收

- `thread_handling=pool-of-threads` 可以启动。
- 单连接能登录、执行 `SELECT 1`、正常断开。
- 认证失败、OOM、worker 创建失败不会泄漏 `Channel_info`、THD、connection count。
- `one-thread-per-connection` 和 `no-threads` 路径不受影响。

### Phase 2 验收

- 空闲连接由 listener 监听 fd，不占用 worker。
- 同一 fd 不会被多个 worker 并发处理。
- KILL idle、shutdown idle、半包请求路径稳定。

### Phase 3 验收

- 长等待能通过 `thd_wait_begin/end` 释放 active worker 配额。
- stall 判断基于 progress counter，不因长查询未完成而频繁误判。
- `thread_pool_max_threads`、oversubscribe、throttling 能限制线程增长。

### Phase 4 验收

- 活跃事务能优先继续执行，Low Queue 不长期饥饿。
- admin port 在普通线程池阻塞时仍可登录排障。
- SHOW STATUS / per-group 观测能解释线程池当前状态。
- 压测报告覆盖 OLTP、锁等待、连接风暴、慢客户端、大结果集。
