# MySQL Thread Pool 架构设计

## 1. 问题背景

MySQL 默认采用 `one-thread-per-connection` 模型（`Per_thread_connection_handler`），每条客户端连接对应一个独立的 OS 线程。此模型在低并发场景下简单高效，但在高并发场景（数千甚至上万连接）下暴露出显著问题：

- **线程切换开销大**：数千线程争抢 CPU，上下文切换频繁，CPU cache miss 急剧上升。
- **资源消耗高**：每个线程消耗独立的内核栈（默认 256KB~512KB），内存占用与连接数线性增长。
- **锁竞争加剧**：大量线程同时竞争 InnoDB 内部锁、MDL 锁，吞吐反而下降。
- **线程创建/销毁开销**：连接风暴时，频繁的 `pthread_create` / `pthread_exit` 成为瓶颈。

Thread Pool（线程池）的核心思想：**将 `num_connections` → `num_threads` 的映射解耦，用固定数量的 OS 线程服务大量连接**，活跃执行线程数收敛到接近 CPU 核数，其余连接排队等待调度。

**Thread Pool 是 MySQL 的第三种连接调度模式，与前两种平级共存，由 `thread_handling` 系统变量控制：**

```
thread_handling 可选值：
  ┌─ one-thread-per-connection -- 每连接一线程（已有，默认）
  ├─ no-threads                -- 单线程处理（已有，用于调试/嵌入式场景）
  ├─ loaded-dynamically        -- 动态连接处理器（已有，插件哨兵值）
  └─ pool-of-threads           -- 线程池调度（新增，本方案）
```

**当 `thread_handling` 不为 `pool-of-threads` 时，所有 Thread Pool 代码完全不加载、不执行。**

### 2.2 核心原则：可选调度模式，对原生代码零侵入

Thread Pool 作为 `SCHEDULER_THREAD_POOL` 调度模式，与现有的 `one-thread-per-connection` 和 `no-threads` 模式**平级共存**，由系统变量 `thread_handling` 控制切换：

```
thread_handling 可选值：
  one-thread-per-connection        -- 每连接一线程（已有，默认）
  no-threads                       -- 单线程处理所有连接（已有）
  loaded-dynamically               -- 动态加载连接处理器（已有）
  pool-of-threads                  -- 线程池调度（新增）
```

**当 `thread_handling` 不为 `pool-of-threads` 时，Thread Pool 代码完全不会被加载/执行，原生 MySQL 的代码路径零影响。**

实现方式：

- **所有 Thread Pool 代码放在独立目录 `sql/threadpool/`** 下，新增内置 `Thread_pool_connection_handler`，只在连接处理器选择点增加分支
- Thread Pool 实现 `Connection_handler` 抽象接口（`add_connection()` / `get_max_threads()`），与 `Per_thread_connection_handler`、`One_thread_connection_handler` 地位相同
- 系统变量 `thread_pool_*` 在 `thread_handling != pool-of-threads` 时属于"不相关变量"，不影响性能
- `do_command()`、`thd_prepare_connection()`、`close_connection()` 等核心函数完全复用，不做任何修改
- 保留 `SCHEDULER_TYPES_COUNT` 作为 `loaded-dynamically` 的哨兵值，不复用它表示内置 thread pool，避免破坏 `my_connection_handler_set()` / `Plugin_connection_handler` 语义

## 3. Thread Group 设计

### 3.1 分组策略

```
group_id = (accepted_connection_seq % thread_pool_size)
```

连接与 thread group **粘性绑定**。同一个连接的所有请求始终在同一个 thread group 内处理，与 MariaDB/Percona 的 round-robin 分组目标一致。由于本方案要求 worker 负责 THD 创建，`add_connection()` 阶段尚未分配 `thread_id`，因此用单调递增的 accepted connection sequence 做分组；THD 创建后把 group 指针写入 scheduler_data。好处是：
- CPU 亲和性，减少 cache miss
- 事务状态（如 MDL 锁、table cache）在 group 内部局部化

缺点：连接数分布不均匀时可能出现负载不均。此问题在实测中影响有限，因为：
- accepted connection sequence 单调递增，在 pool_size 较小时分布近似均匀
- 空闲连接不会长期占用 worker（进入 IDLE 后交给 listener 监听 fd）

### 3.2 Thread Group 数据结构

```cpp
// sql/threadpool/thread_group.h

class Thread_group {
public:
  static constexpr int MAX_THREADS_PER_GROUP = 4096;

  // -- 队列 --
  // 高优先级队列：已有活跃事务的连接
  // 低优先级队列：新连接、或刚从 DORMANT 状态返回的连接
  Connection_queue m_high_priority_queue;
  Connection_queue m_low_priority_queue;

  // -- 线程 --
  int m_active_thread_count;    // 当前活跃线程数 (worker + listener)
  int m_worker_thread_count;    // 纯 worker 数量
  int m_listener_thread_count;  // listener 数量 (0 or 1)

  // -- 状态 --
  std::atomic<bool> m_stalled;  // 是否被 stall detection 标记
  ulonglong m_last_activity_time;  // 最后一次活动时间 (微秒)
  bool m_shutdown;

  // -- 同步 --
  mysql_mutex_t m_mutex;
  mysql_cond_t m_cond_worker;     // worker 等待新连接
  mysql_cond_t m_cond_listener;   // listener 等待新连接

  // -- I/O 等待计数 --
  int m_io_waiting_count;  // 当前阻塞在 I/O 上的线程数

  // -- 连接列表 --
  // 当前 group 中所有活跃连接 (THD) 的链表
  Connection_list m_connections;

  // -- 方法 --
  bool init(uint group_id);
  void destroy();

  // 添加新连接到队列
  void enqueue_connection(THD *thd);

  // 从队列中取出下一个待处理的连接
  THD *dequeue_connection(bool is_listener);

  // Worker 线程的主循环
  void worker_main();

  // Listener 线程的主循环
  void listener_main();

  // Stall 检测相关
  void check_stall();
  void wake_or_create_thread();
};
```

## 4. 连接调度与优先级队列

### 4.1 优先级定义

连接分为两个优先级：

| 优先级 | 场景 | 进入条件 |
|--------|------|----------|
| **High** | 已持有活跃事务、或被 aging 提升的连接 | `thread_pool_high_prio_mode=transactions` 且 `thd_is_transaction_active(thd)`，同时仍有 high-priority tickets；或等待超过 `thread_pool_prio_kickup_timer` |
| **Low** | 新连接、无活跃事务、tickets 用尽的连接 | 默认入口，尤其是可能开启新事务的请求 |

**核心设计理念**：已开始事务的连接不应被新连接阻塞。这避免了事务长时间不提交导致的锁等待链蔓延。

同时必须避免 low priority 永久饥饿：

- 每个连接初始化 `thread_pool_high_prio_tickets`，每次进入 High Queue 消耗 1 张票。
- `thread_pool_high_prio_mode=transactions/statements/none` 兼容 Percona 语义；初版建议默认 `transactions`。
- Low Queue 中等待超过 `thread_pool_prio_kickup_timer` 的事件提升到 High Queue，兼容 MariaDB 的 aging 思路。
- 当 group 已达到 busy/oversubscribe 阈值时，低优先级队列节流，优先让已开始事务的连接释放锁和事务资源。

### 4.2 入队逻辑

```
新连接到达时:
  ┌─ 如果是新连接 → 加入 Low Priority Queue
  └─ 如果是可读连接 (listener 从 epoll/poll 收到事件):
       ┌─ 达到 aging 时间 → 加入 High Priority Queue
       ├─ high_prio_mode=transactions 且事务活跃且 ticket>0 → 加入 High Priority Queue
       ├─ high_prio_mode=statements 且 ticket>0 → 加入 High Priority Queue
       └─ 其他 → 加入 Low Priority Queue
```

后续如果要把 MDL、table lock、global lock、user lock 持有者也纳入 High Queue，应优先在 `thread_pool_priv.h` 增加只读判断 API，而不是直接访问 `THD` 私有成员。

### 4.3 Worker 调度逻辑

```
Worker 线程主循环:
  while (!group->m_shutdown):
    // 1. 优先从 High Priority Queue 取连接
    event = group->high_queue.dequeue()
    if event == NULL:
      // 2. High 为空，尝试从 Low Priority Queue 取
      event = group->low_queue.dequeue()

    if event != NULL:
      // 3. 新连接在 worker 中创建 THD / 认证 / 加入 Global_THD_manager
      if event is Channel_info:
        thd = create_and_prepare_thd(event)
      else:
        thd = event.thd

      // 4. socket 已可读，执行一个 command
      thd->store_globals()
      bool close = do_command(thd)
      // do_command 返回后，连接可能:
      //   - 连接仍存活且 socket 还有缓存数据 → 重新入队
      //   - 连接仍存活但暂无数据 → 注册到 listener 的 epoll/poll
      //   - 连接关闭 → 清理
      //   - 被 kill → 清理
      reset_thread_globals(thd)
    else:
      // 5. 两个队列都为空，进入空闲等待
      if idle_timeout_reached:
        break  // 线程退出
      else:
        cond_wait(&group->cond_worker, timeout)

  // 线程退出前更新线程计数
  group->decrement_active_count()
```

### 4.4 Listener 线程的角色

每个 thread group 最多有 1 个 listener 线程。其职责：

1. **监听网络事件**：维护本 group 的 fd 集合，通过 `epoll`/`poll` 发现可读连接并入队。
2. **保证新连接不被饿死**：worker 全部在处理高优先级请求时，listener 负责分发低优先级队列。
3. **可升级为 worker**：当有请求积压且没有空闲 worker 时，listener 可以升级处理一个请求。
4. **动态调节**：listener 的存在由线程池根据队列情况自动决策，timer 负责兜底创建缺失的 listener。

```
Listener 线程主循环:
  while (!group->m_shutdown):
    events = epoll_wait(group->epoll_fd, timeout)
    for event in events:
      thd = event.data
      group->enqueue_ready_connection(thd)

    if 有积压且没有可唤醒 worker:
      if listener_can_handle_one_event:
        listener 临时转为 worker 执行一个请求
      else:
        创建或唤醒 worker
```

### 5.1 连接事件 / THD 的处理状态

```
                       ┌──────────────┐
    ChannelInfo/THD → │  QUEUED      │  (连接事件在队列中等待)
                       └──────┬───────┘
                              │ worker 取出
                       ┌──────▼───────┐
              ┌─────── │   ACTIVE     │  (执行 do_command)
              │        └──────┬───────┘
              │               │
              │    ┌──────────┼──────────┐
              │    │          │          │
              │    ▼          ▼          ▼
              │ ┌──────┐ ┌──────┐  ┌──────────┐
              │ │DONE  │ │WAIT  │  │ KILLED   │
              │ │(请求 │ │SQL   │  │          │
              │ │完成) │ │      │  └──────────┘
              │ └──┬───┘ └──┬───┘

                   └────┬─────┘

                   │ EXECUTING│  (执行 do_command)
                   └────┬─────┘
                        │
           ┌────────────┼─────────────┐
           ▼            ▼             ▼
     ┌────────┐   ┌──────────┐  ┌─────────┐
     │EXITING │   │  WAIT    │  │  IDLE   │
     │(超时/  │   │ (锁/IO/  │  │ (请求   │
     │ shutdown)│  │ 客户端   │  │完成,回  │
    └────────┘   │ sleep)   │  │到等待)  │
                  └────┬─────┘  └─────────┘
                       │ wait_end
                  ┌────▼─────┐

```

### 5.3 状态转换的触发条件

| 状态转换 | 触发条件 | 备注 |
|----------|----------|------|
| IDLE → EXECUTING | 队列有连接 | `cond_signal` 唤醒 |
| EXECUTING → IDLE | `do_command` 返回，请求处理完成 | 连接存活但 socket 暂无更多数据，交回 listener |
| IDLE → QUEUED | listener 收到 fd 可读事件 | `epoll`/`poll` 检测到新 command 或缓存中已有数据 |
| EXECUTING → WAIT | `thd_wait_begin()` 被调用 | 锁等待、磁盘 I/O、sleep、binlog/group commit 等 SQL 执行等待 |
| WAIT → EXECUTING | `thd_wait_end()` 被调用 | 当前 worker 继续原请求 |
| IDLE → EXITING | 空闲超时 | `idle_timeout` 到期 |
| EXECUTING → EXITING | shutdown | `m_shutdown == true` |

## 6. 网络事件与执行等待

### 6.1 网络 idle/ready 机制

当前 MySQL 没有 `THD_WAIT_NET`。`do_command()` 中的 `my_net_read()` 是阻塞读，不能依赖 `thd_wait_begin()` 自动释放 worker。因此 Thread Pool 必须在调用 `do_command()` 前保证连接 socket 已经可读：

```
连接完成认证后:
  1. thd_get_fd(thd)
  2. group->listener.register_fd(thd, EPOLLIN | EPOLLONESHOT)
  3. thd 状态 = IDLE

listener 收到可读事件:
  1. 如果 thd_connection_has_data(thd) 或 fd 可读
  2. 从 epoll 中临时摘除/disable
  3. 按优先级 enqueue_ready_connection(thd)
  4. 唤醒或创建 worker

worker 执行一个 command 后:
  1. 如果 do_command() 要关闭连接 → 清理 THD
  2. 如果连接仍存活且 socket 缓存还有完整/部分数据 → 重新入队
  3. 否则重新 arm fd，交回 listener
```

Linux 初版建议优先使用 `epoll` + one-shot 模式，避免多个 worker 同时处理同一 fd；非 Linux 平台再用 `poll()` fallback。目标场景是数千到数万连接，每组线性扫描 `poll()` 过早会成为瓶颈。

### 6.2 thd_wait_begin / thd_wait_end 机制

MySQL Server 在 SQL 执行期间的长等待前通过 `thd_wait_begin()` 通知连接处理器，例如 row lock、MDL、table lock、disk I/O、`SLEEP()`、binlog/group commit、sync wait 等：

```cpp
// sql/threadpool/thread_pool.cc

void threadpool_thd_wait_begin(THD *thd, int wait_type) {
  if (is_long_wait(wait_type)) {
    Thread_group *group = get_thread_group(thd);

    // 当前 worker 被阻塞，不再计入可使用 CPU 的 active worker
    group->mark_worker_waiting(thd, wait_type);

    // 如果队列有积压且没有其他 active worker，可以唤醒或创建线程
    if (group->has_queued_events() && !group->has_active_worker()) {
      group->wake_or_create_thread();
    }
  }
}

void threadpool_thd_wait_end(THD *thd) {
  Thread_group *group = get_thread_group(thd);
  group->mark_worker_running(thd);
}
```

该机制只处理 SQL 执行中的等待，不处理连接空闲时的网络读等待。慢客户端、大结果集写阻塞、半包读取仍需要在后续阶段单独评估是否扩展非阻塞网络读写或写事件监听。

## 7. Stall 检测与 Oversubscribe

### 7.1 Stall 定义

一个 thread group 被认为 "stalled"，当：
- group 的 High/Low Queue 或 listener 待分发事件非空
- 自上次 timer 检查以来，没有新的事件被允许 dequeue/开始执行
- group 没有可唤醒的 sleeping worker，或者现有 active worker 都处于长等待/长查询

不要用“`stall_limit` 内没有请求完成”作为唯一条件。长查询可能正常推进但尚未完成，按完成数判断会误判并过度 oversubscribe。

### 7.2 Timer 线程

```
timer_thread_main():
  while (m_timer_running):
    sleep(stall_limit)  // MariaDB/Percona 语义：检查间隔

    for 每个 thread_group:
      snapshot = group->progress_counters

      if group->has_queued_events() &&
         snapshot.dequeue_count == group->last_dequeue_count:
        group->m_stalled = true
        group->wake_or_create_worker_throttled()

      if group->has_queued_events() &&
         group->listener_thread_count == 0 &&
         snapshot.io_event_count == group->last_io_event_count:
        group->wake_or_create_listener()

      // 清理超时空闲线程
      if 存在空闲超过 idle_timeout 且超过 group 最小线程数的 worker:
        signal worker 退出

      group->last_dequeue_count = snapshot.dequeue_count
      group->last_io_event_count = snapshot.io_event_count
```

### 7.3 Oversubscribe 策略

当检测到 stall 或 worker 进入长等待时，允许 group 临时多于 1 个 active worker，但创建线程必须同时满足 per-group 与全局约束：

```
允许创建新 worker，当且仅当:
  1. group 有排队事件或缺少 listener
  2. group 没有 sleeping worker 可唤醒
  3. global_thread_count < thread_pool_max_threads
     或 group_thread_count < 2  // 保证每组至少 listener + worker，避免死锁
  4. group 最近没有在 throttling interval 内创建过线程

group 已 oversubscribed 后:
  - `thread_pool_oversubscribe` 控制最多保留多少 active worker
  - 超过阈值的 worker 在完成当前请求后优先退出或休眠
  - Low Queue 在 active + waiting 达到阈值时节流，避免开启更多新事务
```

因此 `thread_pool_oversubscribe` 不是 `thread_pool_size * N` 的全局线程数公式，而是每个 group 在 oversubscribed 后的 active worker 保留阈值。全局线程上限始终由 `thread_pool_max_threads` 控制。

### 7.4 常见 Stall 场景

| 场景 | 原因 | 线程池行为 |
|------|------|------------|
| 长查询持有行锁 | 多个 worker 被阻塞在锁等待 | 创建额外线程处理其他连接 |
| 慢客户端/网络写阻塞 | worker 阻塞在 `my_net_write()` | 初版记录为风险，通过 stall 临时扩线程；后续评估非阻塞写或写事件监听 |
| 磁盘 I/O 慢 | 所有 worker 在读取数据页 | 创建额外线程（有限） |
| 死锁检测 (innodb) | 所有 worker 在 innodb 锁等待 | 额外线程可能也 block，需要 `innodb_lock_wait_timeout` 配合 |

## 8. 连接生命周期

### 8.1 新连接处理流程

```
客户端 connect()
    │
    ▼
Connection_acceptor::connection_event_loop()
    │  accept() → Channel_info*
    ▼
Connection_handler_manager::process_new_connection(channel_info)
    │  1. check_and_incr_conn_count()
    │  2. m_connection_handler->add_connection(channel_info)
    ▼
Thread_pool::add_connection(channel_info)
    │
    ├── 1. 只接管 Channel_info 所有权，不做认证/握手
    │      // add_connection 在 acceptor 线程调用，必须保持轻量
    │
    ├── 2. group_id = accepted_connection_seq % pool_size
    │
    ├── 3. group->enqueue_new_connection(channel_info)
    │      └── 加入 Low Priority Queue，等待 worker 创建 THD
    │
    └── 4. 如果有空闲 worker → cond_signal(worker)
           如果没有 → 创建新 worker（不超过上限）

Worker 首次处理 Channel_info:
    │
    ├── 1. create_thd(channel_info)
    ├── 2. thd->set_new_thread_id()
    ├── 3. thd_set_thread_stack() + thd->store_globals()
    ├── 4. PSI 绑定 + mysql_socket_set_thread_owner()
    ├── 5. Global_THD_manager::add_thd(thd)
    ├── 6. thd_prepare_connection(thd)  // login_connection + init_connect
    └── 7. 注册 fd 到所属 group 的 listener，等待首个 command
```

### 8.2 连接关闭流程

连接关闭有两种触发路径：

```
路径 A：自然关闭 (客户端断开)
  do_command() 内部 my_net_read() 返回错误
  → end_connection(thd)
  → close_connection(thd)
  → thd->release_resources()
  → Global_THD_manager::remove_thd(thd)
  → Thread Pool 从 group->m_connections / epoll 中移除 thd
  → dec_connection_count()
  → delete thd

路径 B：被 Kill
  thd_set_killed(thd)
  → do_command() 检测到 killed 标记
  → 同上清理流程
```

清理顺序必须对齐 `connection_handler_per_thread.cc::handle_connection()`：`end_connection()` 在 `close_connection()` 前，`release_resources()` 在 `remove_thd()` 前，最后才能 `delete thd`。Worker 切换到另一个 THD 前必须调用 `reset_thread_globals(thd)`，避免 `current_thd`、killable 状态、PSI 线程绑定泄漏到下一条连接。

## 9. 与 MySQL 现有系统的交互

### 9.1 与 THD 对象的绑定关系

```
每个 THD 在 thread pool 模式下通过 `thd_set_scheduler_data()` 关联调度数据，不直接修改 `THD` 结构：
  - m_thread_pool_group: 指向所属 Thread_group
  - m_thread_pool_state:  当前状态 (NEW / IDLE / QUEUED / ACTIVE / WAIT / CLOSING)
  - m_high_prio_tickets:  当前连接剩余高优先级票数
  - m_queue_enter_time:   用于 Low Queue aging / kickup

这些字段通过 thread_pool_priv.h 中已有的 thd_get_scheduler_data() /
thd_set_scheduler_data() 接口存取，避免直接修改 THD 的内部结构。
```

### 9.2 与连接数管理的交互

```cpp
// Connection_handler_manager 已有的计数器:
//   connection_count  -- Thread Pool 模式下含义不变（活跃连接数）
//   max_threads        -- Thread Pool 返回 thread_pool_max_threads

// Thread Pool 新增:
uint Thread_pool::get_max_threads() {
  return thread_pool_max_threads;
}
```

`get_max_threads()` 返回的是连接处理器可能创建的最大 OS 线程数上限，用于连接管理器的全局统计与信号处理路径；实际是否创建新 worker 仍由 per-group 队列状态、sleeping worker、throttling interval 和 `thread_pool_max_threads` 共同决定。

### 9.3 与 KILL 机制的交互

- `thd_set_killed(thd)`：Thread Pool 不会干预，KILL 标记在 `do_command()` 内部检查
- `post_kill_notification`：如果 THD 在队列中等待（QUEUED 状态），直接从队列移除；如果在 listener 中 idle，摘除 fd 并关闭连接
- `close_connection()`：Thread Pool 从 group 的连接列表中移除对应 THD

### 9.4 与 SHOW PROCESSLIST 的兼容

- QUEUED 状态的连接：在 `SHOW PROCESSLIST` 中 `Command` 列显示为 `"Queueing"`
- IDLE 状态的连接：显示为 `"Sleep"`（与原来一致）
- WAIT 状态的连接：保留现有等待/执行状态，由 `thd_wait_begin()` 的 wait type 只影响调度统计

### 9.5 与 stats / status 的交互

```cpp
// 新增 SHOW STATUS 变量:
Threadpool_threads        -- 当前线程池中的线程总数，兼容 MariaDB/Percona 命名
Threadpool_idle_threads   -- 空闲线程数
Threadpool_stalled_groups -- 当前 stalled 的 group 数量
Threadpool_oversubscribed -- 当前 oversubscribed 的 group 数量
Threadpool_queue_length   -- 所有 group 的排队事件数
Threadpool_prio_kickups   -- Low Queue aging 提升次数
```

如果实现成本可控，建议补充只读 I_S/P_S 视图，便于定位单个 group 热点：

| 视图 | 关键列 |
|------|--------|
| `THREAD_POOL_GROUPS` | group_id, thread_count, active_threads, waiting_threads, listener_present, stalled |
| `THREAD_POOL_QUEUES` | group_id, high_queue_length, low_queue_length, oldest_low_wait_ms |
| `THREAD_POOL_STATS` | group_id, dequeued_events, io_events, stalls, oversubscribe_count, prio_kickups |

### 9.6 与全局 THD 管理器的交互

`Global_THD_manager::add_thd()` 和 `remove_thd()` 保持不变，Thread Pool 在连接创建和销毁时正常调用。

### 9.7 与 admin port 的交互

MySQL 已有 `admin_port` / `admin_address`，Thread Pool 必须保留排障入口：

- admin port 连接可以继续走 `one-thread-per-connection` 快速通道，或进入独立的 admin thread group。
- admin 连接不受普通 group 的 Low Queue throttling 影响。
- 当 `thread_pool_max_threads` 达到上限、普通连接都阻塞在全局锁或行锁等待时，仍应能登录执行 `SHOW PROCESSLIST`、`KILL`、提高 `thread_pool_max_threads` 等排障操作。
- MTR 必须覆盖普通端口被阻塞时 admin port 仍可登录。

初版建议采用“admin port 走 one-thread-per-connection 快速通道”，实现最简单，也与 MariaDB `extra_port` / Percona `admin_port` 的 escape hatch 目标一致。

### 9.8 与 Resource Group 的交互

当前 MySQL 在检测到非 `one-thread-per-connection` 或 `thread_pool` 插件时会禁用 Resource Group。内置 `pool-of-threads` 也应明确触发该限制：

- 启动时禁用 Resource Group，并把 unsupported reason 设置为 `Thread pool enabled`。
- 文档和错误信息中说明两者暂不兼容，避免用户误以为 Resource Group CPU 绑定仍然生效。
- 后续若要兼容，必须设计 worker 与 THD/resource group 的 CPU 亲和迁移关系，不能只在 THD 层切换 resource group。

| 变量名 | 类型 | 默认值 | 范围 | 说明 |
|--------|------|--------|------|------|
| `thread_pool_size` | uint | CPU 核数 | 1-512 | Thread group 数量 |
| `thread_pool_max_threads` | uint | 100000 | 1-100000 | 线程池允许的最大线程数；生产建议按线程栈和内存容量下调 |
| `thread_pool_stall_limit` | ulong | 500 | 10-1000000 | Timer 检查间隔与 stall 判定阈值 (ms) |

| `thread_pool_high_prio_mode` | enum | transactions | transactions/statements/none | 高优先级判定模式，兼容 Percona 语义 |
| `thread_pool_high_prio_tickets` | uint | 4294967295 | 0-4294967295 | 每连接可进入 High Queue 的票数，0 表示禁用高优先级 |
| `thread_pool_prio_kickup_timer` | ulong | 1000 | 0-1000000 | Low Queue 等待超过该时间后提升优先级，0 表示禁用 aging |
| `thread_handling` | enum | one-thread-per-connection | - | 取值: `one-thread-per-connection` / `no-threads` / `loaded-dynamically` / `pool-of-threads` |

其中 `thread_handling` 为已有变量。将其扩展增加 `pool-of-threads` 选项。当值为 `pool-of-threads` 时，`Connection_handler_manager::init()` 创建 `Thread_pool_connection_handler` 实例。`loaded-dynamically` 仍由 `SCHEDULER_TYPES_COUNT` 表示，仅供 `my_connection_handler_set()` 动态插件路径使用。

`thread_pool_max_threads=100000` 主要用于兼容 Percona 参数语义，不代表推荐生产值。生产配置应按以下因素下调：

```
推荐上限 <= min(
  max_connections,
  可用于连接线程的内存 / connection_stack_size,
  CPU 核数 * 预期 oversubscribe 上限
)
```

默认文档应提示：如果应用存在大量锁等待、慢客户端或长查询，过高的 `thread_pool_max_threads` 会把 thread pool 退化成大量 OS 线程竞争，失去限流效果。

## 12. 关键设计决策与权衡

### 12.1 粘性分组 vs 动态负载均衡

**选择**：粘性分组（`group_id = accepted_connection_seq % pool_size`）

**理由**：
- CPU cache 亲和性。同一连接的数据（表缓存、MDL 锁）保持在同一个 CPU 核的 cache 中
- MariaDB/Percona 多年的实践验证了这种方案的可行性
- 动态迁移的同步开销可能大于负载不均的损失

**代价**：极端情况下（某连接产生大量事务）可能出现单组过载，通过 oversubscribe 机制缓解。

### 12.2 内置实现 vs 插件实现

**选择**：内置实现（编译进 mysqld），与 `one-thread-per-connection` 平级，通过 `thread_handling` 选择

**理由**：
- 作为 `Connection_handler` 子类直接集成到 `Connection_handler_manager::init()` 的 switch 中，与已有的 `Per_thread_connection_handler` / `One_thread_connection_handler` 模式完全一致
- 不需要通过 `my_connection_handler_set()` 动态加载，避免插件生命周期管理的额外复杂度
- 修改量极小：仅在 `init()` 中新增一个 case + 系统变量注册
- 编译时确定，无运行时加载/卸载开销

**如果未来希望支持运行时切换**，需要在 `THD_event_functions` 基础上增加 `switch_connection_handler()` 回调，并处理已有 THD、fd、listener、timer 的迁移；当前版本不涉及。

### 12.3 epoll vs poll

**选择**：Linux 优先使用 `epoll` + one-shot，`poll()` 作为 fallback

**理由**：
- 目标场景是数千到数万连接，`poll()` 的 O(n) 扫描会在高连接数下过早成为瓶颈
- `EPOLLONESHOT` 可以保证同一连接同一时刻只被一个 worker 处理，状态机更清晰
- MariaDB/Percona 在 Unix 实现中都优先使用平台高效 I/O multiplexing；本方案先聚焦 Linux，其他平台再落到 `poll()` fallback

### 12.4 Native AIO 对比

线程池不与 Native AIO 冲突。Thread Pool 解决的是连接调度层面的并发问题，Native AIO 解决的是 InnoDB 内部磁盘 I/O 的并发问题，两者作用在不同层面，可以共存。

## 14. 实现路线图

### Phase 1：核心框架
- Thread_group 基础结构 + 单队列（无优先级）
- 固定数量 worker 线程（不做动态调节）

- Linux `epoll` listener，`poll()` fallback

- `thd_wait_begin/end` 集成
- Timer 线程 + 基于 dequeue/event progress 的 stall 检测

- High/Low 双优先级队列
- `thread_pool_high_prio_mode` / `thread_pool_high_prio_tickets`
- `thread_pool_prio_kickup_timer` aging 防饥饿
- Low Queue throttling，降低 open transaction 数量
- 系统变量兼容（MariaDB/Percona 参数名兼容）
- admin port、Resource Group、SHOW STATUS / I_S 或 P_S 观测
- 性能测试与调优
- 边界条件处理（shutdown、flush、kill 等）

| 连接限制 | `max_connections`、admin connection、`dec_connection_count()` 回收 |
| KILL | kill active、kill idle、kill queued、shutdown 期间 kill |
| 关闭流程 | `end_connection()`、`close_connection()`、`release_resources()`、`remove_thd()` 顺序 |
| admin port | 普通 group 阻塞时 admin port 仍可登录并执行 `KILL` |
| Resource Group | thread pool 启用时 Resource Group 被禁用且原因明确 |

### 15.2 调度单元测试

- High/Low Queue 顺序、tickets 消耗、`thread_pool_high_prio_mode` 三种模式。
- `thread_pool_prio_kickup_timer` aging 提升，验证 Low Queue 不饥饿。
- 基于 dequeue/event counter 的 stall 判定，避免长查询正常运行时误判。
- per-group oversubscribe、线程创建 throttling、`thread_pool_max_threads` 达到上限。
- listener one-shot rearm，确保同一 fd 不会被两个 worker 并发处理。
